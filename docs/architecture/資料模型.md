# 資料模型

- 文件狀態：維護中
- 對應階段：Phase 9
- 最後核對日期：2026/10/22

畫面讀寫的是瀏覽器 IndexedDB，以 Dexie 操作。Phase 9 起每個帳號一個資料庫 `foodbuddy-{userId}`，並同步到伺服器的 SQLite（第五節）。登入前的舊資料庫 `foodbuddy` 只在第一次登入時讀取並搬家。
定義在 [db/db.ts](../../client/src/db/db.ts)，型別在 [types/index.ts](../../client/src/types/index.ts)。

## 一、資料表

| 資料表 | 主鍵 | 索引 | 說明 | 使用中 |
|--------|------|------|------|------|
| `places` | `id`（UUID） | name、city、district、priceRange、*cuisines、*mealTimes、*tags、updatedAt | 店家基本資料 | ✅ |
| `userPlaces` | `placeId` | *statuses、rating | 使用者對店家的狀態、評分、備註 | ✅ |
| `tags` | `name` | | 已使用過的 Tag（輸入提示與管理） | ✅ |
| `searchHistory` | `id` | createdAt | AI 搜尋歷史 | ✅ |
| `visits` | `id` | placeId、visitedAt | 到訪紀錄 | ✅（Phase 7 起使用；刪店家時一併刪除） |
| `dismissed` | `id`（OSM id） | dismissedAt | 按過「沒興趣」的推薦店家（name、dismissedAt） | ✅（Phase 8，v3） |
| `outbox` | `key`（`{collection}|{id}`） | | 待上傳的變更：collection、id、ts（本機修改時間）；不同步 | ✅（Phase 9，v4） |
| `meta` | `key` | | 同步 cursor、上次同步時間；不同步 | ✅（Phase 9，v4） |

`*` 表示多值索引（陣列）。

把「店家」與「我對這間店的看法」分成 `places` 與 `userPlaces` 兩張表，對應 Agenda 第 19 節的 Place／UserPlace。列表顯示時合併成 `PlaceWithUser`。

## 三、版本與升級

| Dexie 版本 | 變更 | 升級處理 |
|------|------|------|
| 1 | 初始五張表 | — |
| 2 | `places` 新增 `*mealTimes` 索引 | 舊資料補 `mealTimes: []` |
| 3 | 新增 `dismissed` 資料表 | 不需轉換 |
| 4 | 新增 `outbox`、`meta`（雲端同步） | 不需轉換；舊資料庫 `foodbuddy` 不升級，登入後搬到帳號資料庫 |

新增版本時用 `db.version(N).stores({...}).upgrade(...)`，不要修改舊版本的定義。

## 四、資料存取

所有頁面只透過 repository 讀寫，不直接操作 `db`（Tag 輸入提示與搜尋歷史的唯讀查詢除外）：

- [placeRepository.ts](../../client/src/db/placeRepository.ts)：list、get、create、update、remove、toggleStatus、setRating、setLocation（補座標，不更新 updatedAt）
- [tagRepository.ts](../../client/src/db/tagRepository.ts)：listWithCount、rename（同名合併）、remove
- [visitRepository.ts](../../client/src/db/visitRepository.ts)：listWithPlace、listByPlace、create、update、remove、markNotRecommended（寫入後同步店家狀態與評分）

- [dismissedRepository.ts](../../client/src/db/dismissedRepository.ts)：list、ids、add、remove

AI 口味分析的結果（`foodbuddy.tasteInsight`）與首頁為你推薦的結果（`foodbuddy.forYou`）存在 localStorage，不在 IndexedDB，也不同步；登出時清除。
`foodbuddy.lastUser`（離線時用來開啟本機資料）與 `foodbuddy.legacyHandled.{userId}`（是否已詢問過搬家）也在 localStorage。

## 五、雲端同步（Phase 9）

### 前端
- [db.ts](../../client/src/db/db.ts) 的 Dexie DBCore middleware：每個讀寫交易自動把 `outbox` 加入範圍。
- 對 6 張同步資料表的 add、put、delete、deleteRange，都在同一個交易裡寫一筆 outbox：key 為 `{collection}|{id}`，同一筆重複修改只留最新一筆。
- 從伺服器拉回的資料用標記過的交易寫入，不會再進 outbox。
- [syncEngine.ts](../../client/src/sync/syncEngine.ts) 的一輪同步：
  1. 讀 outbox，取當下資料，讀不到代表已刪除。
  2. 上傳，一次最多 200 筆、約 4MB。
  3. 收到回應後，在同一個交易裡刪除已上傳、且上傳期間沒再被修改的 outbox。
  4. 套用其他裝置的變更；本機還有未上傳修改的資料先跳過。
  5. 更新 cursor。有 hasMore 或 outbox 還有資料就繼續下一輪。

### 伺服器（SQLite，[AppDbContext.cs](../../server/FoodBuddy.Api/Data/AppDbContext.cs)）

| 資料表 | 說明 |
|------|------|
| `AspNetUsers` 等 | ASP.NET Core Identity；`AppUser` 加上 DisplayName、CreatedAt |
| `SyncRecords` | Id、UserId、Collection、RecordId、Data（整筆 JSON；刪除後為 null）、Deleted、Version（每個使用者遞增）、ClientUpdatedAt（前端修改時間） |

- 唯一索引 (UserId, Collection, RecordId)；索引 (UserId, Version)。
- 刪除帳號時，SyncRecords 透過外鍵一併刪除。
- 衝突：ClientUpdatedAt 較新的贏。較舊的修改不寫入，並把伺服器版本傳回給送出的裝置。
- 結構變更用 EF Core migration（[Data/Migrations](../../server/FoodBuddy.Api/Data/Migrations/)），後端啟動時自動套用。
