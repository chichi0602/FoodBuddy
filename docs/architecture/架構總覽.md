## 二、前後端分工

| | 前端 | 後端 |
|---|---|---|
| 資料 | 畫面讀寫瀏覽器 IndexedDB（每個帳號一個資料庫），背景同步 | 帳號（ASP.NET Core Identity）與資料正本（SyncRecords），存在 SQLite |
| 登入 | 登入頁、401 時回到登入頁 | HttpOnly Cookie；Email＋密碼、Google；AI 與找座標需登入 |
| AI | 不接觸金鑰 | 代理 Azure OpenAI，金鑰從 User Secrets 讀取 |
| 外部資料 | — | 查詢 OpenStreetMap（Nominatim、Overpass），結果快取在記憶體 |
| AI 結果快取 | — | 解析需求 1 小時、推薦結果 10 分鐘（以請求內容雜湊為 key；「換一批」不命中），都在後端記憶體 |
| 計算 | 篩選、排序、距離、口味摘要、收藏初步比對 | 地理編碼、候選店家、範圍內收藏、AI 排序與合併 |

**為什麼畫面仍讀本機資料庫**：Phase 1～8 是個人使用，資料只放瀏覽器。Phase 9 要公開上站、每人一個帳號。如果改成每次都打 API，48 處 `useLiveQuery` 都要重寫，而且斷網就不能用。
所以保留 Dexie 當畫面的資料來源：每筆寫入由 middleware 記進 outbox，`syncEngine` 在背景和伺服器交換變更。換裝置登入會自動下載資料。詳見 [資料模型](資料模型.md) 第五節。

## 三、AI 找美食的資料流

```
瀏覽器                         後端                          外部服務
─────────                     ──────                        ─────────
輸入需求 ──POST /parse──────► AzureOpenAiService ─────────► Azure OpenAI（gpt-5，解析）
         ◄── 條件 ────────────
（沒地點時取得定位）
收藏＋口味摘要
  ──POST /recommend─────────► RecommendationService
                               ├ OsmPlaceSearchService ───► Nominatim（地名→座標）
                               │                       ───► Overpass（範圍內店家）
                               ├ 選出範圍內的收藏
                               └ AzureOpenAiService ──────► Azure OpenAI（挑選與分析）
         ◄── 收藏區＋新店（含 preferenceReason）
分三區顯示，加入時寫入 IndexedDB
```

開發時前端透過 Vite 代理把 `/api` 轉到後端（[vite.config.ts](../../client/vite.config.ts)），預設 `http://localhost:5122`，可用環境變數 `API_URL` 改寫。

## 四、外部服務

| 服務 | 用途 | 注意事項 |
|------|------|----------|
| Azure OpenAI（gpt-5 系列） | 解析需求、挑選與分析店家 | 直接呼叫 v1 REST API，不用 SDK（正式版 SDK 當時不支援 gpt-5）；沒有金鑰改用 Mock |
| Nominatim | 地名轉座標 | 公益服務：必須帶可辨識的 User-Agent、每秒最多一次；快取 24 小時 |
| Overpass API | 查詢範圍內的餐飲店家 | 公益服務、偶爾忙碌；主站＋備援站，快取 24 小時 |
| OpenStreetMap 圖磚 | 地圖底圖（Phase 6） | 志工維運，使用政策不允許大量使用；個人使用可，公開服務需改用付費或自架圖磚 |
| Google Fonts | Huninn 粉圓體 | |
| Google Maps | 只用「開啟搜尋連結」，不呼叫 API | |

## 五、防止 AI 虛構店家

1. 店家只能來自 Overpass 的查詢結果。
2. 結構化輸出的 `candidateId` 用 enum 限定為候選清單內的 id。
3. 伺服器再驗證一次，不在清單的結果丟棄。
4. 店名、座標、地址等事實欄位一律用 OSM 資料，AI 只負責分析文字。
