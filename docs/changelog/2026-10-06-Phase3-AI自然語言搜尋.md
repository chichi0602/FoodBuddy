# Phase 3：AI 自然語言搜尋

- 文件狀態：已實作（推薦來源已於 Phase 4 改為 OpenStreetMap）
- 對應階段：Phase 3
- 最後核對日期：2026/10/06

## 變更目的

需求 Agenda 第 6～9 節：使用者用一句話描述需求，AI 先解析成結構化條件，再推薦店家並附上分析。
這是系統最重要的核心功能。

## 與使用者確認的決策

| 問題 | 使用者的選擇 |
|------|------|
| Azure 部署的模型 | **gpt-5 系列**（推理模型：不送 temperature、用 `max_completion_tokens`、可設 `reasoning_effort`，支援 json_schema 結構化輸出） |
| 還沒串外部店家資料時，推薦從哪來 | AI 依自身知識推薦，**每間附 Google Maps 連結並標示「資訊可能過時，請確認」** |
| 解析出的條件要不要順便搜「我的美食」 | 現在就做基本版（原排在 Phase 5） |

## 怎麼生成

### 後端

- **不用 Azure SDK，直接呼叫 REST API**：當時正式版 `Azure.AI.OpenAI` 2.1.0 使用的 API 版本太舊，不支援 gpt-5。改用 `HttpClient` 呼叫 Azure OpenAI v1 路徑 `{endpoint}/openai/v1/chat/completions`，header 帶 `api-key`。設定 `ApiVersion` 不是 `v1` 時改走舊版 deployments 路徑。
- [AzureOpenAiService.cs](../../server/FoodBuddy.Api/Services/AzureOpenAiService.cs)：兩次呼叫
  - **解析**：`reasoning_effort: minimal`，實測約 4 秒
  - **推薦**：`reasoning_effort: low`，實測約 16～20 秒
  - 部署不接受某個 `reasoning_effort` 值時，自動拿掉該參數重試一次（不同 gpt-5 版本支援的值不同）
  - 錯誤一律轉成中文訊息（驗證失敗、找不到部署、請求過多、逾時、回應過長），不外洩金鑰或原始錯誤
- [AiSchemas.cs](../../server/FoodBuddy.Api/Services/AiSchemas.cs)：json_schema strict 結構化輸出。strict 模式要求每個欄位都列在 required，選填欄位用 `["string","null"]` 表示。
- [MockAiService.cs](../../server/FoodBuddy.Api/Services/MockAiService.cs)：沒有金鑰時用規則解析（城市、行政區、料理、時段、人數、預算），回傳明顯標示「示範」的資料，讓整個流程照樣能跑。
- [AiController.cs](../../server/FoodBuddy.Api/Controllers/AiController.cs)：`POST /api/ai/parse`、`POST /api/ai/recommend`，需求限 500 字，AI 失敗回 502＋中文訊息。
- [Program.cs](../../server/FoodBuddy.Api/Program.cs)：依金鑰是否設定齊全，註冊 Azure 或 Mock 服務。

### 前端

- [services/aiApi.ts](../../client/src/services/aiApi.ts)：呼叫後端並統一錯誤訊息。
- [pages/AiSearchPage.tsx](../../client/src/pages/AiSearchPage.tsx)：取代 `/ai` 的佔位頁，支援從首頁帶入 `?q=`。
- [components/RecommendationCard.tsx](../../client/src/components/RecommendationCard.tsx)：推薦卡片（符合度圓環、推薦原因、推薦餐點、網路評價、優缺點、一鍵加入）。
- [utils/aiMatch.ts](../../client/src/utils/aiMatch.ts)：`matchCollection`（用條件比對收藏，地名寬鬆比對：高雄＝高雄市、臺＝台）、`findSaved`（推薦的店是否已收藏）、`recommendationToPlace`。
- `Place` 新增選填 `aiSummary`：從 AI 加入時保存當時的分析，詳細頁「AI 整理」卡片顯示。
- [vite.config.ts](../../client/vite.config.ts)：代理目標可用 `API_URL` 環境變數改寫（測試時用來指向不同後端）。

## 功能介紹

- 輸入需求 → 「AI 理解的需求」以標籤呈現（📍地區、🍽料理、🕒時段、👥人數、💰預算、#關鍵字），**按 × 移除任一條件就會重新推薦**。
- 「我的收藏符合條件」：符合地區與料理的收藏，排除不推薦，想再訪與收藏優先，符合時段或預算的會加提示標籤。
- 「AI 推薦」：5 間店，可「換一批」（排除目前這 5 間）、一鍵加入想去／收藏／標記去過；已在收藏中的顯示「已在我的美食」。
- 最近 5 筆搜尋可一鍵重搜。
- 沒有金鑰時顯示「目前顯示的是示範資料」。

## ⚠️ 踩到的問題與修正

- **Mock 的「換一批」沒有結果**：示範店名固定 5 個，排除後就沒了。改成準備 10 個名稱。
- **兩個請求互相取消**：新搜尋開始時，上一次的解析如果剛好回來，會呼叫推薦並取消新的請求。解析回來後先檢查是否已被取消。
- **使用者看到「搜尋條件有誤，請調整後再試一次」**：實際原因是使用者開著的後端是改版前啟動的，沒有 `/api/ai/*`，回應 404。程式沒錯，重開後端即可；同時把 404 的訊息改成「後端還沒有 AI 功能，請重新啟動後端後再試」，避免誤導。
- Windows 的 curl 傳中文參數會變亂碼，後端測試改用 Node 腳本送 UTF-8。

## 刻意的取捨

- 推薦只靠模型知識，店名大多真實但地址、價格可能過時，所以卡片都附 Google Maps 連結與提醒。這個限制在 [Phase 4](2026-10-06-Phase4-串接OpenStreetMap.md) 解決。
- 解析與推薦拆成兩次呼叫：解析很快，畫面可以先顯示條件，不必等 20 秒才有反應。

## 驗證

- 真實 Azure OpenAI：文件範例「高雄左營，三個人晚餐，每人 500 元左右的日式料理」解析為 高雄市／左營區／日式／晚餐／3 人／$500，與 Agenda 第 6 節完全一致。
- Playwright：Mock 12 項、真實 AI 8 項全部通過（解析、收藏比對、推薦、加入想去、移除條件重推、換一批、後端斷線錯誤、詳細頁 AI 整理、最近搜尋、手機版）。
- 測試用的伺服器都開在其他連接埠（5123／5124／5174／5175），不影響使用者自己開著的 5122／5173。
